Spinzar Gems Co.

Luxury gemstone showcase & inquiry platform

A Bangkok gemstone dealer needed a website as good as the stones. I built all of it: the database, the API, the admin dashboard, the public site and the deployment.

The brief

The dealer wanted a site that looks as good as the stones. Not a shop with a cart. Gems like these get sold through a conversation, so the site has two jobs: show the stone properly, and make it easy to ask about it.

That's the whole brief, and it shaped every decision below.

The key decision: inquiry, not checkout

There are no customer accounts and no payments on this site. That's on purpose. A visitor browses, finds a stone, then either sends an inquiry or taps WhatsApp to start a chat.

Why

This is a product decision, not a missing feature. A checkout would have meant accounts, payment handling and a lot more to break, for a sale that happens in conversation anyway.

How it works, with plain examples

Search that forgives typos

People misspell gemstone names all the time. The search is built so a wrong spelling still finds the stone.

Example: typos in the search box
You typeYou still find
saphireSapphire
rubyyRuby

The bug that taught me how it works. My first version measured similarity against the whole string, so a typo got compared with an entire stone name. The long name diluted the score, and good matches ranked too low. Switching to word-level similarity, where each word is compared on its own, fixed it.

Prices in four currencies

Every price shows in USD, THB, EUR and GBP. Exchange rates refresh daily. If the rate service is down, a fallback keeps prices on screen instead of leaving the page broken.

Data that can't be quietly damaged

An inventory system fails in boring ways: someone deletes the wrong stone, or two people overwrite each other. So the rules are enforced, not hoped for.

  • No hard deletes. A stone is retired, never erased.
  • Valid status flow only. A stone can only move between statuses in an allowed order.
  • Stale edits are rejected. If two staff members open the same stone and both save, the second save is refused instead of silently overwriting the first.
  • Append-only history. Every change is logged, and the log only grows.

An admin dashboard with roles

Staff manage inventory, inquiries and other staff from one dashboard. What each person can do depends on their role.

Images and gem certificates

Each stone has photos and a PDF certificate. Uploads are validated on the server, not just in the browser, and then stored in cloud storage.

Privacy built in

Customer details can be anonymised on request, GDPR/PDPA-style.

The details

Custom 404 pages, optimised images, a sitemap and robots file for search engines, and 20 routes in total.

Bugs I'm glad I hit

Route ordering

The API matches routes in the order they're declared. Put a general route above a specific one and it swallows the requests meant for the specific one. Reordering fixed it, and the order is something I check now.

A DELETE that failed only in the browser

It passed every direct API test and still failed on the real page. The cause was CORS: browsers enforce it and testing tools don't. Lesson: test in the browser, not just against the API.

A collapsed layout

A section of the page collapsed because of how an image was sized. Sizing the image properly fixed it.

Decisions I made

  • Inquiry only. The site starts conversations. It doesn't try to close sales.
  • No payment processing. Less to build, less to break.
  • One platform for everything. The public site, the admin dashboard and the API are one build.
  • Skipped what wasn't needed. I left out features that didn't earn their place.
