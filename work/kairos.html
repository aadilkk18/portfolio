Kairos

An AI decision-intelligence platform. Most of us make big decisions with scattered information and no real structure. Kairos separates what you actually know from what you are only assuming, does the maths properly, and never pretends to be more certain than it is.

The name

Ancient Greek had two words for time. Chronos is the kind you measure: seconds, hours, deadlines. Kairos is the right moment: the window when conditions are actually right to act. Kairos, the product, is a bet on the second one.

The problem

People decide with half the facts.

Career switches, big purchases, life calls. People make them with half the facts in their head and no structure, so they either overthink or guess.

The obvious fix is to ask an AI. But if you ask an LLM “which job offer is better?”, you get a smooth, confident answer with no calculation behind it. It cannot show its working, it cannot tell you how fragile the answer is, and it may well have made up the numbers.

The one rule

The LLM narrates. It never calculates. Every number in a Kairos report is computed by a deterministic engine, and the LLM only explains what the engine found.

How it works

Take a decision most people face: two job offers. Here is what Kairos does with it, step by step. The numbers below are made up to show the mechanics, but the method is the one the engine runs.

  1. You describe the decision in plain language.You type “comparing two job offers”. You do not build a model or fill in a template.
  2. Kairos builds the model for you.It creates a domain and works out the objectives that matter: compensation, commute, growth, flexibility, culture.
  3. Each objective is grounded, or honestly rated.If an objective can be tied to real data, Kairos finds it. If it cannot, it falls back to a scale you rate yourself.
  4. You review the model.You adjust the objectives, set how much each one matters, add constraints and confirm the data. Nothing runs on assumptions you have not seen.
  5. Engine A analyses it.Four methods run on the same model: scoring, simulation, sensitivity analysis and a check on how stable your priorities are.
  6. The report explains it.The LLM writes the explanation around results the engine computed.

Objectives, and what each one needs

Salary has a currency value. Commute has a time. But “culture” has no universal number, and I refuse to let Kairos invent one just because it is convenient. So each objective is handled according to what it really is.

Scoring the options (MCDA)

To compare a salary with a commute, everything has to be put on the same 0 to 1 scale. Kairos does that using fixed reference points: a worst case and a best case for each objective, decided before the options are scored. Here, salary runs from 100 (worst) to 300 (best), commute from 90 minutes (worst) to 0 (best), and the three rated objectives use a 1 to 10 scale.

Each score is (value minus worst) divided by (best minus worst). Multiply by the weight, add them up, and Offer A leads, but only by 0.03. That is close, and Kairos knows it. The scale range matters: a 0 to 10 scale, as in the car domain, gives different scores for the same rating.

Why fixed reference points

Many scoring methods rescale against the best and worst options in the current list. Add a third option and the scale shifts, so A and B can swap places even though nothing about A or B changed. That is called rank reversal. With fixed reference points, adding or removing an option never changes how the others compare. I chose this over TOPSIS and AHP, and the approach is based on published methods.

Simulation

Real numbers are not exact. A salary offer might shift a little. A commute changes every day. So instead of testing one fixed set of values, Kairos runs the comparison hundreds of times, nudging the uncertain values by a realistic margin each time (about 5% for a quoted salary, about 15% for a commute estimate).

Example result

Across hundreds of runs, Offer A came out ahead in about 91%. So A is the likely winner, but not a certainty, and the report says exactly that instead of declaring a flat winner.

There is a trap here that I fixed. If a domain has no volatility set, the simulation quietly does nothing and every run is identical, which looks like stability but is really a missing input. Kairos detects that case and tells the report not to present it as evidence.

Sensitivity analysis

Next question: what would change the answer? Kairos takes one entered figure, such as a salary or a resale value, and finds how far it would have to move before the ranking flips. The importance weights are covered by the stability check below.

Example result

Offer A leads by 0.03. If Offer A’s salary fell from 170 to about 150, roughly 12%, Offer B would take the lead. So this decision is sensitive to that one number, and that is far more useful to know than “A wins”.

Stability across weightings

People are rarely sure of exact percentages. They know “salary matters most, then growth”. The stability check handles that. It uses SMAA with ordinal weight constraints: it keeps your order of importance, tries thousands of different weight combinations that fit that order, and counts how often each option wins.

Example result

Keeping salary first and growth second, Offer A wins under about 94% of reasonable weightings. Strong, but not total.

If this check disagrees with the main score (say, the main score picks A but most weightings pick B), the report is not allowed to give a confident recommendation and has to name both options. I added that rule after a live test showed the report recommending a winner that the stability check did not support.

Weights from answers

Asking someone for exact percentages is unreliable, so Kairos can turn a handful of answers into weights using a Best-Worst Tradeoff method. The stability check then samples around those weights. It is wired into the report routes and tested, and I ran it live once on the real car domain, where the weights matched a hand calculation.

There is no questionnaire interface yet, so for now this runs behind the scenes.

The report

All of the above goes into a plain-language report. The LLM writes the explanation, but it is boxed in.

  • The model is told not to state figures itself. The key sentences are written by code from the computed results and inserted into the report: how often the leader wins across weightings, the smallest change that would flip the ranking, and the overall holds-up-but-sensitive statement. The model writes the explanation around them.
  • Figures that cannot be traced to computed data are listed under “Unverified figures worth double-checking”. This check is best-effort, not a guarantee.
  • A close result is not called a clear win.
  • A check removes sentences that the computed facts contradict, for a fixed list of wordings. A false claim such as “no other factor could change this” can still be written, and paraphrases can slip through.
Example: how the example would read

“Offer A comes out slightly ahead, and it wins in about 91% of simulated outcomes. But this is close. Offer A’s salary would only have to fall by about 12% for Offer B to take the lead. The biggest unknowns are your own ratings for culture and growth, so those are worth a second look before you decide.”

In the real system, the sentences that carry figures are written by code and inserted, not written by the model.

Testing

There are 699 automated tests passing. For the newer guard code I went further and mutation-tested it: I deliberately broke the code to check that the tests fail. The gaps that turned up were closed with new tests.

Design decisions

Never invent a number

If something has no real measure, Kairos says so and asks you to rate it. A made-up figure would make the whole answer look more precise than it is, which is the exact failure Kairos exists to avoid.

One engine for every domain

I did not want a car calculator and a job calculator. Engine A has no domain-specific logic. A domain is a thin configuration that lists objectives and units. I tested it on two unrelated decisions, buying a car and comparing job offers, and the same engine handled both.

Honest about uncertainty

Close results are called close. Missing data is called missing. The report is built to inform a decision, not to pretend the decision has already been made.

Saved decisions

Decisions and analysis snapshots are saved, so you can come back and see what the numbers said at the time.

Reliability

The server protects against duplicate requests with idempotency keys. Calls to the LLM API go through a circuit breaker with retry on rate limits, and tokens are tracked.

Known gaps

  • There is no login or per-user authorization. It is a single-user tool for now.
  • The weights questionnaire is not built.
  • Automatic web research from option entry is not built.

What’s next

Web research. You should not have to type in every data point. Ask about iPhone 17 Pro vs Galaxy S26 Ultra vs Pixel 10 Pro and Kairos should research the specs itself. But it cannot trust online numbers blindly. Each value has to stay tied to its objective and be reviewable before it is used. That raises a harder question: how does Kairos decide whether something is even measurable? Finding a number is not the same as finding the right one.

Engine B. Engine A handles what numbers can model. Engine B is for the decisions a spreadsheet cannot hold: career direction, relationships, values. It will use real frameworks instead of vibes, and it will be honest that some things can only be informed, never predicted. It is not started, and I will not pretend otherwise.
