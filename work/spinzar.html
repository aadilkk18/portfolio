Spinzar Gems Co.

A luxury gemstone showcase and inquiry platform. A Bangkok gemstone dealer needed a website as good as the stones. I built all of it: the database, the API, the admin dashboard, the public site and the deployment.

The brief

A site as good as the stones.

The dealer wanted a site that looks as good as the stones. Not a shop with a cart. Gems like these get sold through a conversation, so the site has two jobs: show the stone properly, and make it easy to ask about it.

That is the whole brief, and it shaped every decision below.

The key decision

There are no customer accounts and no payments on this site. That is on purpose. A visitor browses, finds a stone, then either sends an inquiry or taps WhatsApp to start a chat.

This is a product decision, not a missing feature. A checkout would have meant accounts, payment handling and a lot more to break, for a sale that happens in conversation anyway.

Search that forgives typos

People misspell gemstone names all the time. The search is built so a wrong spelling still finds the stone.

The bug that taught me how it works

My first version measured similarity against the whole string, so a typo got compared with an entire stone name. The long name diluted the score, and good matches ranked too low. Switching to word-level similarity, where each word is compared on its own, fixed it.

Prices in four currencies

Every price shows in USD, THB, EUR and GBP. Exchange rates refresh daily. If the rate service is down, a fallback keeps prices on screen instead of leaving the page broken.

Data that cannot be quietly damaged

An inventory system fails in boring ways: someone deletes the wrong stone, or two people overwrite each other. So the rules are enforced, not hoped for.

  • No hard deletes. A stone is retired, never erased.
  • Only valid status changes. A stone can move between statuses only in an allowed order.
  • Stale edits are rejected. If two staff members open the same stone and both save, the second save is refused instead of silently overwriting the first.
  • The history is append-only. Every change is logged, and the log only grows.

The admin dashboard

Staff manage inventory, inquiries and other staff from one dashboard. What each person can do depends on their role.

Images and certificates

Each stone has photos and a PDF certificate. Uploads are validated on the server, not just in the browser, and then stored in cloud storage.

Privacy

Customer details can be anonymised on request, GDPR and PDPA style.

The details

Custom 404 pages, optimised images, a sitemap and robots file for search engines, and 20 routes in total.

Bugs I’m glad I hit

Route ordering

The API matches routes in the order they are declared. Put a general route above a specific one and it swallows the requests meant for the specific one. Reordering fixed it, and the order is something I check now.

A DELETE that failed only in the browser

It passed every direct API test and still failed on the real page. The cause was CORS: browsers enforce it and testing tools do not. The lesson was to test in the browser, not just against the API.

A collapsed layout

A section of the page collapsed because of how an image was sized. Sizing the image properly fixed it.

Decisions I made

  • Inquiry only. The site starts conversations. It does not try to close sales.
  • No payment processing. Less to build, less to break.
  • One platform for everything. The public site, the admin dashboard and the API are one build.
  • I skipped what was not needed. I left out features that did not earn their place.
